# AutoCore v1.6.1 live dashboard guide

## Data flow

```text
Browser dashboard (dashboard/index.html)
       | GET /api/state ; POST /api/action
       v
Python standard-library HTTP bridge (127.0.0.1)
       | JSON-lines commands / JSON state
       v
Persistent C++ simulation process (autocore_engine)
       |
       v
VehicleNetwork -> Engine ECU / Battery ECU / Body ECU / Diagnostics ECU
```

The server binds only to `127.0.0.1`. It hosts the HTML, JSON state/action API, health endpoint and telemetry CSV export. The Python process validates the request and maps it to a fixed C++ command. The C++ engine owns ECU state, the drive-cycle profile, CAN telemetry, DTC state, snapshots and events. The server ticks the C++ engine every 100 ms while running; the browser polls every 500 ms.

## Dashboard pages

- **Overview:** RPM, coolant temperature, battery voltage, active DTC count, rolling signal charts, four ECU presence cards and recent events. The prominent **Run self-test** button opens Scenario Lab and starts the guided test.
- **CAN Network:** recent in-process Classic CAN frames, ID, symbolic message name, DLC, payload, CRC status, frame count/rate and CSV export. The runtime CSV message catalogue lists 5 messages / 16 signals. The ID/mask control filters only the visible monitor stream; Diagnostics ECU monitoring remains unfiltered. Frames are generated by the simulator, not captured from a physical bus.
- **Diagnostics:** active-fault count, stored-DTC count, decoded UDS request/response, three DID read controls, DTC count/record read, freeze-frame read, session, Tester Present, simulated reset acknowledgement, clear-DTC and the six-monitor catalogue.
- **CAN Controller Health:** per-ECU TEC/REC, Error Active/Error Passive/Bus-Off state, TX/RX counters, error injection and 128-step recovery.
- **Scenario Lab:** guided self-test, live fault monitor cards, start/pause/reset, throttle, headlights/door controls, paired sensor demonstration, and six individual fault injectors.
- **Event Log:** timestamped actions, DTC transitions, UDS requests and filterable log history.

## Understand the DTC display

A healthy new simulation starts with **0 active DTCs**. This is the correct baseline. The Diagnostics page nevertheless lists six supported diagnostic monitors in the catalogue as `NOT SET`. This means no fault has been detected yet; it does not mean the diagnostic logic is absent.

When a fault is injected, its DTC begins as `PENDING (1/3)` after the first failed observation, remains pending on the second and becomes `ACTIVE / CONFIRMED` on the third consecutive failed observation. For sensor monitors this is approximately 300 ms at the 100 ms ECU update interval. Communication DTCs first wait for the >500 ms timeout, then apply the same three-sample qualification. After recovery, the current failure/pending bits clear while simplified confirmed/history status can remain as `RECOVERED / CONFIRMED` or `RECOVERED / HISTORY`. UDS service `0x14` clears the modeled records and snapshots.

## Guided self-test — recommended first demonstration

Use **Run self-test** from the top bar or open Scenario Lab and press **Run all diagnostic tests**. Avoid other controls while it is running. The browser sends actual API actions to the C++ engine and checks:

1. Engine overtemperature → P0217 active, UDS DTC read, freeze-frame snapshot.
2. Battery undervoltage → P0562 active, UDS DTC read, freeze-frame snapshot.
3. Engine ECU offline → wait for U0100 timeout DTC.
4. Battery ECU offline → wait for U0111 timeout DTC.
5. CRC corruption → AC0001 active and latched until recovery.
6. Rolling-counter sequence gap → AC0002 active and latched until recovery.
7. UDS service group → DIDs F40C/F405/F411, extended session 0x10, Tester Present 0x3E, simulated ECU Reset acknowledgement 0x11, and final DTC read.

Each fault scenario is recovered before the next. The expected completion message is `COMPLETE: 7 / 7 test groups passed`. Historical DTC records remain for review while active faults return to zero.

## Quick manual sensor demonstration

1. Open Diagnostics and click **Inject P0217 + P0562**.
2. Wait for coolant to reach 126 °C and battery voltage to reach 10.45 V. The active DTC count should be 2.
3. Allow three consecutive 100 ms monitor observations for the faults to become confirmed. The first sample is pending; the third is confirmed.
4. Click **Read DTC records**. The UDS response should begin `59 02 2F` and list matching records.
5. Select P0217 in the freeze-frame selector and click **Read snapshot**. The response begins `59 04 00 02 17` and contains the captured sensor snapshot in multi-frame ISO-TP form.
6. Click **Recover all**. Wait for valid telemetry and active DTC count 0.
7. Click **Clear DTC information (0x14)** if you also want to remove recovered history and snapshots.

## Individual scenarios

| Control | Expected monitor result |
|---|---|
| Engine overtemperature | Engine coolant 126 °C; P0217 |
| Battery undervoltage | Battery voltage 10.45 V; P0562 |
| Engine ECU offline | No engine telemetry for >500 ms; U0100 |
| Battery ECU offline | No battery telemetry for >500 ms; U0111 |
| CRC corruption | Invalid CRC telemetry; AC0001 |
| Rolling-counter gap | Unexpected counter successor; AC0002 |
| Recover all | Restores sensors/ECU transmission and lets monitors clear active DTC state |

## UDS response conventions used by this project

| Request | Positive response prefix | Meaning |
|---|---|---|
| `22 F4 0C` | `62 F4 0C` | Engine RPM |
| `22 F4 05` | `62 F4 05` | Coolant temperature |
| `22 F4 11` | `62 F4 11` | Battery voltage in mV |
| `19 02 2F` | `59 02 2F` | DTC record list matching the modeled status mask (includes pending status) |
| `19 04 <DTC> 01` | `59 04 <DTC>` | Snapshot record 1 |
| `10 03` | `50 03` | Extended session accepted |
| `3E 00` | `7E 00` | Tester Present acknowledged |
| `11 01` | `51 01` | Simulated reset acknowledgement |
| `14 FF FF FF` | `54` | Clear modeled DTC information |

The dashboard also translates common positive responses into readable messages while retaining raw hexadecimal bytes for technical inspection.

## Operational notes and troubleshooting

- Start with `Run_AutoCore.bat` or the documented manual server command; do not open the HTML with `file://`.
- Keep the launcher terminal open during use. Ctrl+C stops the server and its C++ engine child process.
- If Overview works but there are no active DTCs, run the self-test; a zero-fault baseline is expected.
- If a fault shows `INJECTED / MONITORING`, allow at least one telemetry cycle (100 ms) or, for ECU-offline scenarios, more than 500 ms.
- CRC/counter demonstration DTCs remain visible until Recover all, to avoid being missed between 500 ms UI polls.
- The in-memory event/frame/history windows are bounded; telemetry CSV exports the most recent rolling history.
- This is an educational host model, not a physical vehicle tool or certified diagnostic stack.


## CAN Controller Health page

This page is a controller-level fault-confinement demonstration, separate from the six DTC sensor/communication/integrity monitors. It displays four controller records. Each row has TEC, REC, state, transmit success/error totals, receive success/error totals, enabled error injectors and Bus-Off recovery count/progress. The summary cards count Error Active, Error Passive and Bus-Off controllers.

### Interpret the counters

- **TEC** is the Transmit Error Counter. An injected TX error adds 8. A successful transmit reduces nonzero TEC by 1.
- **REC** is the Receive Error Counter. An injected RX error adds 1. A successful receive reduces it; if it is above 127, a successful receive reduces it to 127 in this model.
- **Error Active:** both counters are below 128.
- **Error Passive:** TEC or REC is at least 128, but TEC has not reached 256. An Error Passive node can still communicate.
- **Bus-Off:** TEC reaches 256. The node stops transmitting in the virtual network.

### Demonstrate TX-driven Error Passive

1. Reset simulation/counters for a clean baseline.
2. Select Engine ECU.
3. Click **24 TX errors · Error Passive**. From TEC 0, the 24 events add 192. The row should show TEC 192 and `ERROR_PASSIVE`.

### Demonstrate Bus-Off and peer-network continuity

1. Reset simulation/counters again.
2. Select Engine ECU and click **32 TX errors · Bus-Off**. From TEC 0, the events add 256.
3. Verify Engine changes to `BUS_OFF` and its ECU availability changes to Offline.
4. Open CAN Network. Engine `0x100` frames should stop, while Battery `0x110` and Body `0x120` frames continue.
5. Wait for Engine telemetry timeout and DTC qualification; `U0100` should progress to confirmed.

### Demonstrate Bus-Off recovery

1. Return to CAN Controller Health with Engine selected.
2. Switch off all continuous TX error injectors. Recovery is blocked while any persistent TX injector is on.
3. Click **Start Bus-Off recovery**.
4. Watch the recovery sequence counter advance to 128/128. One distinct 100 ms virtual tick represents one eligible sequence observation. Repeated updates at the same timestamp do not count.
5. At 128/128, TEC/REC reset, state returns to Error Active and Engine telemetry resumes.
6. Check Diagnostics for U0100 recovery and Event Log for Bus-Off/recovery transitions.

### Demonstrate RX-driven Error Passive

1. Reset simulation/counters.
2. Select Battery ECU.
3. Click **128 RX errors · Error Passive**. REC should reach 128.
4. With valid receptions restored, REC can fall and the state can return to Error Active.

### Persistent error toggles

Continuous TX errors add 8 TEC for each scheduled TX attempt until the ECU becomes Bus-Off. Turn the toggle off before recovery. Continuous RX errors add 1 REC for each incoming frame received by the selected controller; turn it off to allow successful receptions to reduce REC. Reset between independent demos.

### Important model limitation

The 128 recovery count is a visible discrete approximation. One count per distinct 100 ms simulation tick represents one abstract eligible 11-recessive-bit observation. This is not the real time required by a physical CAN controller and does not simulate physical bits, ACKs or error flags. Read `can_fault_confinement.md` for full details.
